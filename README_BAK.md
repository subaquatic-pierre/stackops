# Developer Knowledge Base Portfolio — Blueprint

## 1. Core Vision & Philosophy

- **The Concept:** A docs-style, public engineering garden hosted on GitHub Pages.
- **The Goal:** A searchable, living archive of technical execution, architectural thinking, domain learning, and operational experiences that scales with every project built.
- **Design Mindset:** Low friction for writing, high clarity for reading, and explicit organization over implicit magic.

---

## 2. Structural Engines (Docusaurus Allocation)

### A. The Docs Engine (Hierarchical / State-Driven)

_Persistent, structured knowledge organized by topic rather than time._

- **Projects & Case Studies:** Long-lived technical profiles, blueprints, and retrospectives of systems.
- **Engineering Wiki:** Persistent technical domain knowledge, architectural deep dives, and low-level specifications.
- **Runbooks:** Step-by-step operational scripts and procedures optimized for quick navigation.

### B. The Blog Engine (Chronological / Timeline-Driven)

_Immutable historical records tied to a specific point in time._

- **Incident Reports:** Post-mortems documenting real-world system failures, timelines, root causes, and resolutions.
- **Architectural Decision Records (ADRs):** Point-in-time snapshots of technical choices, rationales, and context.
- **Changelogs & Technical Essays:** Logs of progress, project launches, and narrative thoughts.

---

## 3. High-Level Taxonomy & Navigation Ideas

### Taxonomy Options

- **Flat Structure:** A dedicated top-level directory and sidebar category for every type of technical artifact.
- **Nested Hubs:** Grouping content into logical operational pillars (e.g., separating outward-facing project deep dives from internal operational documentation).
- **Tag-Driven Discovery:** Using global cross-cutting tags (e.g., specific languages, database engines, or infrastructure layers) to slice through different content types.

### Cross-Cutting Relationships to Resolve

- **Project-Centric vs. Global Records:** Deciding whether historical artifacts like ADRs and runbooks should live nested inside their respective project directories or grouped globally by data type.
- **The Operational Loop:** Mapping out how incident records tie back to updated wiki troubleshooting entries and new runbook creation.

---

## 4. Content Schemas to Standardize

- **Project / Case Study Blueprint:** Focusing on problem definition, architectural blueprints, trade-offs, and production post-mortems.
- **Wiki / Troubleshooting Blueprint:** Tracking symptoms, investigative methods, commands executed, findings, and preventive measures.
- **Incident Report Blueprint:** Structuring timelines, root cause analysis (e.g., the 5 Whys framework), and explicit actionable tracking.
