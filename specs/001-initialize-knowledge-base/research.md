# Research: Initialize Knowledge Base Reference

**Feature**: Initialize Knowledge Base Reference  
**Date**: 2026-07-31

## Decisions & Rationale

### 1. Docs landing page strategy

**Decision**: Create `docs/welcome.mdx` and configure it as the docs index using Docusaurus front matter `slug: /`.

**Rationale**:
- Docusaurus allows any doc to serve as the category/index root via the `slug` front-matter field.
- Using `slug: /` on `docs/welcome.mdx` makes `/docs/` resolve to the welcome page instead of an auto-generated folder index.
- This avoids the need for a custom plugin or swizzled DocPage component.

**Alternatives considered**:
- Rename `intro.mdx` to `welcome.mdx` and keep `sidebar_position: 1`. Rejected because the slug approach gives the welcome page a cleaner URL and explicit role as the docs root.
- Create a custom React page at `src/pages/docs.tsx`. Rejected because it would duplicate Docusaurus docs-plugin layout and sidebar handling.

### 2. Autogenerated sidebar with flat domain folders

**Decision**: Keep `sidebars.ts` as autogenerated (`dirName: '.'`).

**Rationale**:
- With top-level folders `aws/`, `kubernetes/`, and `linux/` directly under `/docs/`, Docusaurus automatically renders each folder as an expandable category containing its documents.
- Files inside each folder are flat (no nested folders), so the category listing directly reflects the flat structure required by the constitution.
- Maintenance cost is zero when adding new domains or documents.

**Alternatives considered**:
- Manual sidebar with explicit category definitions. Rejected because it adds maintenance overhead for a first-phase structure that is expected to grow.
- Hybrid manual/autogenerated sidebar. Rejected as unnecessary; the autogenerated ordering (alphabetical by filename) is acceptable for the first phase.

### 3. Search plugin

**Decision**: Install `@easyops-cn/docusaurus-search-local` to provide client-side search across the knowledge base.

**Rationale**:
- Docusaurus does not include search functionality by default.
- The feature specification includes Success Criterion SC-003: "Search returns relevant results for at least three domain-specific keywords."
- A local search plugin satisfies this criterion without requiring an external service such as Algolia DocSearch.

**Alternatives considered**:
- Defer search to a later phase. Rejected because SC-003 is part of the current feature's success criteria.
- Use Algolia DocSearch. Rejected because it requires application approval and external indexing, which is disproportionate for a first-phase knowledge base.

### 4. Front-matter schema validation

**Decision**: Document the required front-matter schema in a contract file and rely on code review/convention rather than a build-time validator.

**Rationale**:
- Docusaurus does not enforce custom front-matter schemas at build time.
- Adding a validator (e.g., Zod, remark plugin) would introduce a new dependency and tooling step beyond the scope of this first phase.
- The spec requires `title`, `description`, and `tags`; optional `last_updated` and `draft`. Clear seed documents and documented conventions are sufficient for now.

**Alternatives considered**:
- Add a remark plugin to validate front matter. Rejected to keep the first phase lightweight and aligned with the "no testing" constraint.
- Use JSON Schema with a pre-commit hook. Rejected because it adds tooling not required for the initial rollout.

### 4. Handling removed `/docs/intro` links

**Decision**: Update hardcoded references in `docusaurus.config.ts` (navbar and footer) and remove the `intro.mdx` file.

**Rationale**:
- `docusaurus.config.ts` has `onBrokenLinks: "throw"`, so any remaining link to `/docs/intro` will fail the build.
- The navbar currently uses a `docSidebar` item, which automatically points to the first doc in the sidebar. After removing `intro.mdx` and adding `welcome.mdx` with `slug: /`, the sidebar root becomes the welcome page.
- The footer explicitly links to `/docs/intro` and must be updated to `/docs/` (or removed).

**Alternatives considered**:
- Keep `intro.mdx` as a redirect. Rejected because it leaves placeholder content in the knowledge base.
- Use Docusaurus plugin-client-redirects. Rejected as overkill for a brand-new site with no external bookmarks to preserve.

### 5. Seed document examples

**Decision**: Use realistic, concise examples for each domain and content type.

**Rationale**:
- Realistic examples establish patterns for authors (naming, front matter, voice, structure) better than lorem-ipsum stubs.
- Each example should be short enough to serve as a template but complete enough to demonstrate the expected format.

**Pattern for actionable documents**:
- Front matter: title, description, tags
- Sections: Objective, Prerequisites, Procedure (with commands), Verification

**Pattern for reference documents**:
- Front matter: title, description, tags
- Sections: Overview, Key Concepts, Common Locations/Examples, See Also

## Open Questions Deferred to Later Phases

- Custom MDX components (terminal windows, special callouts) are explicitly out of scope per the spec assumptions.
- Tag page customization and tag taxonomy governance are deferred until the knowledge base grows.
