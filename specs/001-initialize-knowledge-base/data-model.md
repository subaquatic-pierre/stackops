# Data Model: Initialize Knowledge Base Reference

**Feature**: Initialize Knowledge Base Reference  
**Date**: 2026-07-31

## Overview

The knowledge base is a static content graph derived from the filesystem under `/docs/`. There is no runtime database; the "data model" is the set of conventions that Docusaurus uses to generate pages, sidebars, and tag indexes.

---

## Entity: Domain

A top-level knowledge area represented as a folder directly under `/docs/`.

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | string | yes | Folder name used in URLs and sidebar (e.g., `aws`, `kubernetes`, `linux`). |
| `name` | string | yes | Human-readable label derived from folder name (e.g., `AWS`, `Kubernetes`, `Linux`). |
| `path` | string | yes | Relative filesystem path from repository root (e.g., `docs/aws/`). |
| `documents` | Document[] | yes | Flat list of MDX documents contained directly in the domain folder. |

### Validation rules

- Domain folders MUST be created directly under `/docs/`; no nested folders are allowed inside a domain folder.
- A domain SHOULD contain at least one actionable and one reference document during the first phase.

---

## Entity: Document

An MDX file that is either an actionable playbook or a reference article.

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | string | yes | File basename without extension (e.g., `revoke-leaked-iam-keys`). |
| `title` | string | yes | Display title from front matter. |
| `description` | string | yes | Short summary from front matter, used for SEO and indexes. |
| `tags` | string[] | yes | Keywords from front matter used for discovery and tag pages. |
| `type` | enum | yes | `actionable` or `reference`. Inferred from naming convention and content pattern. |
| `domain` | Domain | yes | The domain folder that contains the document. |
| `slug` | string | yes | URL path segment generated by Docusaurus from the file path. |
| `last_updated` | ISO date | no | Optional front-matter field indicating when the document was last reviewed. |
| `draft` | boolean | no | Optional front-matter field; if `true`, Docusaurus excludes the document from production builds. |

### Validation rules

- Document filenames MUST follow the convention:
  - Actionable: `verb-noun-context.mdx` (e.g., `revoke-leaked-iam-keys.mdx`)
  - Reference: `noun-context.mdx` (e.g., `vpc-architecture-overview.mdx`)
- Document IDs MUST be unique within their domain folder.
- Every document MUST include `title`, `description`, and `tags` in its front matter.
- Document body SHOULD follow the content pattern defined for its type.

---

## Entity: Tag

A keyword used to classify and discover documents across domains.

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | string | yes | Tag value as written in front matter (e.g., `iam`, `security`, `playbook`). |
| `documents` | Document[] | yes | All documents that include this tag in their front matter. |

### Validation rules

- Tags SHOULD be lowercase and hyphenated (e.g., `incident-response`, not `Incident Response`).
- Tags SHOULD include the domain name, relevant tools, and content type (`playbook`, `reference`, `manifest`).
- The same tag ID MAY appear on documents in different domains.

---

## Relationships

```text
Domain 1--* Document
Document *--* Tag
```

- A Domain contains many Documents.
- A Document belongs to exactly one Domain.
- A Document has many Tags.
- A Tag may be associated with many Documents across multiple Domains.

---

## Content Type Patterns

### Actionable document pattern

Used for playbooks, procedures, and copy-paste commands.

Recommended sections:
1. **Objective** — what the reader will accomplish.
2. **Prerequisites** — required tools, permissions, or context.
3. **Procedure** — numbered steps with commands.
4. **Verification** — how to confirm the procedure worked.

### Reference document pattern

Used for explanations, architectures, and config locations.

Recommended sections:
1. **Overview** — what the topic covers.
2. **Key Concepts** — definitions and relationships.
3. **Common Locations / Examples** — paths, manifests, or sample outputs.
4. **See Also** — related documents or external resources.
